Helping people recover when a file fails

A product proposal for Veyra, the browser video editor. One-page PRD, policies and five wireframes.

Status: proposal, not built. November 2026. Drafted with Claude Code from Veyra's current source. It has not been tested with users, and the targets below still need baselines.

Problem

Video files are often cut off, unusual or in a format the browser can't decode. Veyra's shared error panel explains what went wrong and offers one link, "Report this problem". It has no shared next step.

  • The report link opens a new page, so the file and settings on the tool page are lost.
  • Sending a report needs an email app or a GitHub account, or copying the text by hand.
  • People who only want their video finished have to work out the fix themselves.

Goal and scope

Goal: someone whose file fails can see a likely fix, try it without choosing the file again, and report the problem if it doesn't work.

In scopeOut of scope
Single-file tools: error panel, suggested fix, retry, short reportThe timeline editor, accounts, live chat, uploading any video for support

User journey

  1. Choose a file
  2. File fails
  3. See cause and fix
  4. Try the fix
  5. Download, or report

Wireframes

Requirements

Cause (existing error code)What the user seesSuggested fix
unsupported-codecYour browser doesn't support this formatCompatibility page, or another copy
corruptThis file looks damagedTry repair, then retry in place
no-tracksThis file has no video (or no sound)Choose another file or a suitable tool
no-encoderYour browser can't create this outputPick another output format
too-large, out-of-memoryThis file is too big for this deviceClose other tabs, or use a smaller file
validation-failedThe result didn't pass our checksRetry once, then report
unknownSomething went wrongRetry once, then report

The other existing codes use the unknown treatment in the first version.

Must also: keep the file and settings while the panel is open, never offer a fix that can't apply, work by keyboard and screen reader, and work at phone width.

Policies

  • Privacy: reports never include the video or its name. Browser details are optional and visible before sending.
  • Permission: no repair or retry starts until the user asks for it. The original file is never changed.
  • Triage: data loss or a wrong output comes first, then failures affecting several people, then single unusual files.
  • Repeat reports: three reports with the same tool and cause trigger a product review: fix it, improve the message, or document the limit.

How we'd know it works

MeasureBaselineFirst target
People who recover after a failure in a moderated testNot known4 of 5 with a fixable file
Reports that include the tool and causeNot known9 in 10
Repeat reports for the same causeNot knownFalling month on month

These use moderated tests and reports people choose to send, so no new tracking is needed.

QA before launch

  • Each error code shows the right message and only fixes that apply.
  • File and settings survive opening and closing the report panel.
  • A successful repair still passes Veyra's output checks.
  • The report contains no file name or file content.
  • Keyboard, screen reader, phone width, and Chrome, Edge and Firefox.

Open questions

  • How often does each error occur? There is no data yet.
  • Which damaged files can the repair tool really fix?
  • Is email, GitHub or copy the easiest way to report?
